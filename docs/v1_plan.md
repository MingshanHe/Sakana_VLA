# SakanaVLA v1 改进计划：简化结构、提高闭环性能

日期：2026-11-09　|　基于 [report.md](report.md) 的 v0 结果（闭环 SR 0%，离线 ADE 3.2 cm）

这份计划先列出我在代码和数据里核对到的**具体问题**，再按优先级给出改进项。每一项都写清楚：做什么、为什么、预期效果、成本、怎么验证。

---

## 0. 核对到的事实

这些都是在当前代码、训练日志和评测结果里直接查到的，不是推测。

| # | 事实 | 影响 |
|---|---|---|
| 1 | 动作专家 233M 参数的分布：**线性注意力层 119M（51%）**，MLP 103M，**真正读 VLM 的全注意力层只有 9.8M（4%）**。原因是 `make_expert_config` 把宽度缩到 640，但线性注意力的头数和头维度（16 × 128）是照抄 VLM 的，没有一起缩。 | 一半的参数花在最不重要的地方 |
| 2 | 18 层线性注意力只作用在 13 个 token 上（1 个状态 + 12 个动作）。 | 线性注意力是为长序列设计的，在 13 个 token 上几乎没有意义 |
| 3 | 训练和推理时 **fla 的快速路径都没有生效**（`policy_server.log` 里有 "The fast path is not available ... Falling back to torch implementation"），VLM 和专家的线性注意力都在跑慢的 torch 实现。 | 训练只有 3.2 it/s（205 样本/s）；专家推理也比应有的慢 |
| 4 | 专家的全注意力只有 **2 个 query head**（和 KV head 数相同，这是为了直接复用 VLM 的 K/V）。VLM 自己是 8 个 q head / 2 个 KV head（GQA）。 | 专家和 VLM 之间的"读取带宽"很窄 |
| 5 | 图像 256² 只产生 **64 个视觉 token**（16 px 的 patch，2×2 合并，每个 token 覆盖 32×32 像素）。 | 中等大小的目标在图里只占 1–4 个 token，很难 grounding |
| 6 | 起点时只有 **12%** 的 episode 能看到目标，前 2 秒内也只有 29%。 | 开局基本是"搜索"，单帧无法决定往哪转 |
| 7 | 起点帧（前 1 秒）只占训练帧的 6.4%，stop 帧占 6.7%。 | 最难、最关键的两段数据最少 |
| 8 | `stop` 是和位移一起用 flow matching 回归 ±1 得到的，没有独立的分类头。 | 阈值不好校准；遮图时模型一次都不停，说明它对 stop 的判断很脆弱 |
| 9 | 执行器在**第一次** stop 投票时就让无人机原地悬停 0.5 s（`chunks[i, :, :4] = 0`）。训练数据里"静止 + 零转速"只在终点出现。 | 一次误判会制造出"像已到达"的画面，诱导第二次 stop，自我强化 |
| 10 | `results.json` 里每条 episode 的 `frames` 是整批（同一栋房子）的帧计数，不是这条自己的结束时间。 | 没法分析"什么时候停/撞"，要修 |
| 11 | 闭环评测只有 32 条，"到过目标附近" 22% 对 12.5% 只差 3 条。 | 结论噪声大 |

## 1. 改进项（优先级从高到低）

### P0　不重新训练就能做的诊断和修复（约半天）

**P0.1　执行器：tentative stop 不要悬停。**
- 做法：第一次 stop 投票时，继续飞上一个 chunk 剩下的 0.5 s，而不是原地悬停；连续 2 次（或 3 次）才真的停。
- 为什么：打断事实 9 里的自我强化循环。
- 验证：同一个 checkpoint，32 条 unseen，看"主动停下且在目标附近"的比例和错误 stop 的数量。
- 成本：10 行代码，几分钟评测。

**P0.2　评测修正。**
- 每条 episode 记录自己的结束帧和结束原因；评测集固定为 64 条 unseen + 32 条 val_seen；保留遮图和打乱指令两组对照。
- 加一个**离线分段指标**：把验证帧按"起点 0–2 s / 中途 / 终点前 2 s"分开算 ADE、朝向误差、stop 的准确率和召回率。这会直接告诉我们误差集中在哪一段。
- 成本：半小时代码，GPU 上几分钟。

**P0.3　修好 fla 快速路径**（装 `causal-conv1d`，确认 GPU 上不再出现 fallback 警告）。
- 如果做了 P2（去掉专家里的线性注意力），专家这边就不需要了，但 VLM 的前向仍然受益。

### P1　让模型知道"进度"（最可能直接提高 SR）

目标：解决"起点就停"和"原地打转"（事实 6、7；视频 #15、#158、#155）。

**P1.1　状态里加进度特征。**
- 在现在的 5 维状态（机体速度、转速、高度）上加：已飞时间、已飞距离、累计转角、上一个执行的动作（最近 5 步 × 5 维）。
- 数据侧：都能从 `observation.states` 直接算；仿真侧：执行器本来就有这些量。
- 预期：起点（时间 = 0）和终点（时间 > 0、距离 > 0）立刻可分；"上一步在左转"也能让前后两次决策保持一致。
- 成本：数据和执行器各 20 行；重训 stage A 约 85 分钟。

**P1.2　加历史帧。**
- 2 张历史帧（t−1 s 和 t−2 s）缩到 128²（每张约 19 个 token）+ 当前帧 256²（67 个 token）。prefix 从约 100 token 增加到约 140，VLM 计算量增加不到一半。
- 这是 OpenFlyV2 Base 配置的"瘦身版"（它用 4 张同分辨率的历史帧，token 数是 5 倍）。
- 执行器要维护每架无人机的帧缓冲；训练数据从同一 episode 取前面的帧，开头不够就重复第一帧。
- 验证：P0.2 的起点分段指标；闭环"5 s 内就停"的比例；SR。
- 成本：一天代码 + 重训。

先做 P1.1，再做 P1.2；如果 P1.1 已经把起点误 stop 压下去，P1.2 可以延后。

### P2　简化并加强动作专家（省 85% 参数，更快，不应变差）

**P2.1　去掉 18 层线性注意力。**
- 专家只保留 6 个全注意力层（对应 VLM 的第 3、7、11、15、19、23 层）+ 各自的 MLP，约 37M 参数（现在 233M）。
- 为什么：事实 1–3。这些层既占一半参数，又在跑慢路径，又只作用在 13 个 token 上。去掉后也不再依赖 `flash-linear-attention` / `causal-conv1d`。
- 如果担心容量：中间方案是 12 层，6 层读 VLM 的 K/V，6 层只在 suffix 内做自注意力（约 70M）。
- 验证：离线 ADE/FDE/stop F1 不差于现在的 3.2 cm / 6.3 cm / 0.88；训练速度明显提高。

**P2.2　query head 从 2 个改成 8 个（GQA）。**
- 和 VLM 一致：8 个 q head 分 4 组共用 VLM 的 2 个 KV head。HF 的注意力实现自带 `repeat_kv`，应该不用改别的（要验证）。
- 只多 1.5M 参数（q_proj 640 → 2048），但专家读 VLM 的"带宽"变成 4 倍。

**P2.3　stop 改成独立的分类头。**
- 状态 token 的输出接一个线性层，预测"这个 chunk 内要停"和"每一步是否停"，用 BCE；flow matching 只管 4 维位移。
- 好处：推理时可以调阈值、看概率校准；闭环里可以用更稳的规则（比如概率连续 2 次 > 0.7）。
- 验证：stop 的准确率/召回率（用 P0.2 的分段指标），尤其是起点段的误报。

P2.1–P2.3 一起做一次重训就能验证，建议和 P1.1 合并成同一个 v1 版本。

### P3　Grounding：放开 VLM，加目标框辅助任务

目标：解决"认错目标"和"到了不停"（视频 #139、#157）；让遮图/打乱指令两组对照和主模型拉开差距。

**P3.1　Stage B：放开 VLM。**
- 从 stage A 的 checkpoint 继续训练 8k 步：VLM 的语言部分 lr 1e-5，专家 lr 1e-4。视觉编码器可以先冻结，再试放开。
- 风险：数据只有 1,700 条 episode、模板指令，VLM 容易过拟合。所以要配合 P3.2，并且盯住 val_unseen。
- 成本：显存和时间大约是 stage A 的 3 倍（约 4 小时）。

**P3.2　目标框辅助任务。**
- 在 suffix 里加一个 "target" query token，输出目标框 (x, y, w, h) 和"是否可见"，L1 + BCE，权重 0.1–0.5。监督信号是数据里现成的 `observation.boxes` / `observation.target_pixels`。
- 为什么：强迫模型把指令里的 "television" 和画面里的像素对上。这个任务的 IoU 本身也是一个能监控的 grounding 指标。
- 即使 VLM 冻结，这个辅助任务也能训练专家去"找"目标，所以可以先在 stage A 里加。

**P3.3　图像分辨率。**
- 先把 256² 上采样到 384²（147 个 token）试试，数据不用改；如果有效，再考虑重新渲染 448²（视觉 token 约 200 个，每栋房子 90 s）。
- 事实 5 说明现在的 64 个 token 对小目标太粗了。

### P4　数据

**P4.1　消除开局多解。** 两个方案选一个：
- (a) 搜索规则统一：看不到目标时专家固定向左转，直到路径方向进入视野。这样"看不到目标就左转"是一个单帧就能学会的确定性规则。
- (b) 起点朝向偏向第一段路径（±45° 以内）。更简单，但模型学不到"搜索"。
- 两者都要重新生成数据（55 栋约 1.5 小时 GPU）。

**P4.2　更多纠偏数据。**
- 扰动从 50% 提高到 100%，每条 1–2 次，幅度更大。
- DAgger：让当前模型飞 3–8 s，再让专家从那个状态接管并记录。专家的重规划（`GoalField.path`）本来就支持从任意点出发，改动不大。这是解决"偏离后撞墙（75%）"最对症的办法。

**P4.3　更多房子。** 55 → 150 栋（Train200 还有 145 栋没用）。unseen 继续固定用 47–56，再加 10 栋。

**P4.4　指令改写。** 按原计划用 LLM 改写模板指令，再人工校对。模板的问题见 report.md 3.6 节。这项主要配合 P3。

### P5　工程和效率（随手做）

- 训练吞吐现在 205 样本/s。修 fla 快速路径（P0.3）、P2.1 去掉线性注意力、用 `use_fast=True` 的图像处理器、batch 128，预计能到 2 倍以上。
- 推理：5 步 Euler 够用；可以测 3 步是否一样好。
- 时间集成（temporal ensembling）：把相邻两次 chunk 重叠的部分平均，减少 replan 时的抖动。
- 闭环评测现在每 32 条约 2–6 分钟，很适合快速迭代，保持这个速度。

## 2. 建议的实验顺序

| 轮次 | 内容 | 需要重训 | 预计时间 | 看什么 |
|---|---|---|---|---|
| 1 | P0.1 执行器 stop + P0.2 评测修正 + P0.3 fla | 否 | 半天 | 错误 stop 数量；起点/中途/终点分段误差 |
| 2 | **v1-a** = P1.1 进度状态 + P2.1–2.3 专家简化 + P3.2 目标框辅助（VLM 仍冻结） | 是（stage A，<85 min） | 1–2 天 | 离线不变差；起点误 stop 下降；SR、到达目标附近 |
| 3 | **v1-b** = v1-a + P1.2 历史帧 | 是 | 1 天 | 起点和打转问题；SR |
| 4 | **v1-c** = Stage B（P3.1）+ P3.3 分辨率 | 是（约 4 h） | 1–2 天 | 遮图/打乱指令对照拉开差距；bbox IoU；#139 类错误 |
| 5 | P4.1 + P4.2 数据重生成，DAgger 一轮，重训 | 是 | 2–3 天 | 碰撞率；SR |

决策规则：
- 第 2 轮如果离线指标变差超过 10%，先回退 P2.1 到 12 层方案，再继续。
- 第 3 轮如果 SR 仍然低于 10%，说明瓶颈在 grounding，直接进第 4 轮，数据改动放后面。
- 每一轮都在同一个固定的 64 条 unseen 集上评，并保留遮图/打乱指令对照。

一个粗略的目标：v1 在 64 条 unseen 上 **SR ≥ 30%，碰撞 ≤ 40%**。这是估计，不是承诺。

## 3. 现在不建议做的事

- 把 MAM / MSP 加回来：先把基础版做对，再考虑。
- 换更大的 VLM：当前瓶颈不在 VLM 大小，而在进度信息、grounding 和数据。
- RL 微调或真机：闭环 SR 还是 0，还不到这一步。
- 重新设计数据格式：现在的 LeRobot 格式字段够用，所有新特征都能从现有字段算出来。
